# 六書造字堂第二輪遊戲化審查（G2-01–G2-10）

- 審查基準：`c0b136f`
- 審查日期：2026-08-07
- 邊界：只檢查並修改成長、儲存、閃卡、自測、對戰、戰績及 logic tests；不新增空成就、不以點擊或重玩偽造學習進度。
- 與上一輪的差異：上一輪 G01–G10 解決「成長循環是否存在」；本輪檢查同一循環的計量公平、模式隔離、回饋可信度與失敗後能否立刻恢復。

## G2-01｜閃卡排程與練功日使用不同日界線

- 程式證據：基準版 `js/store.js` 的 `today()` 直接使用 `Math.floor(Date.now() / 86400000)`（UTC）；`LSProgress.localDateKey()` 卻使用 `Asia/Taipei`。台灣 00:00–07:59 之間，連續學習已跨日，卡片到期日仍停在前一天。
- 影響：玩家會遇到「今天已開始修行，但今天的到期卡還沒到」的節奏矛盾。
- 修正策略：新增 `learningDayNumber()`，所有 Leitner `due` 建立、評分與查詢統一採台灣日界線；既有數字 `due` 不改格式。
- 可驗收條件：UTC 15:59:59 與 16:00:00 的學習日序號相差 1；舊存檔的數字 `due` 可照常比較。

## G2-02｜「模糊」被算成答對與連勝

- 程式證據：基準版 `gradeCard(id, 1)` 會同時執行 `right++`、`streak++`，雖不升盒，卻可替下一次作答累積精通所需證據。
- 影響：主觀承認「只記得一點」也能推高精通，破壞熟練度公平性。
- 修正策略：「模糊」維持原盒、隔天再出現、清除連勝，記為需要補強；只有「熟」能增加 `right` 與連勝。
- 可驗收條件：第 3 盒卡按「模糊」後仍在第 3 盒，`right` 不變、`streak=0`、隔天到期。

## G2-03｜到期卡滿載會讓新字永久沒有位置

- 程式證據：基準版 `buildDeck()` 先用弱點與到期卡填滿 20 格，之後才補新字；只要每天有 20 張到期卡，探索循環便完全停止。
- 影響：長期玩家只剩清債，缺乏新鮮感與可見擴張；新字庫內容無法進入學習循環。
- 修正策略：一般回合最多保留 4 格新字、弱點仍至多占一半；玩家主動指定補強牌組時，尊重其選擇，不強塞新字。
- 可驗收條件：30 張到期卡且仍有新字時，20 張牌組恰含 4 個新字；指定弱點仍排在牌組最前。

## G2-04｜未作答類別被誤判為最弱類別

- 程式證據：基準版 `weakestCats()` 把未作答類別設為 `rate=-1`，排序會壓過已有大量錯題的真弱項。
- 影響：「補強弱項」額外題位優先給未知類別，玩家的實際錯誤沒有被優先處理，回饋失真。
- 修正策略：排序改為「有真實錯題 → 未作答探索 → 已全對」，真實錯題內再依正確率排序。
- 可驗收條件：指事 2/5、象形 9/10、會意 5/5、其餘未作答時，前三順位為指事、象形、第一個未作答類別。

## G2-05｜對戰與每日字陣會污染一般自測難度

- 程式證據：基準版 `adaptiveLevel()` 直接讀 `quiz.recent` 全部 20 筆；`recordAnswer()` 又把對戰寫入同一陣列，每日字陣則偽裝成 `quiz`。
- 影響：打低階大師的高分可能把下一次一般自測推到挑戰級；每日固定題重玩也可操縱難度，挫折並非來自真實能力變化。
- 修正策略：保存 `quiz`、`daily`、`battle` 三種模式；自適應與近期正確率只採一般自測，舊紀錄缺少 mode 時仍視為 quiz 以維持相容。
- 可驗收條件：一般自測連錯 5 題、對戰連對 15 題後，自適應仍為基礎且一般自測近期正確率為 0%。

## G2-06｜重入與每日重玩會重複灌入成長

- 程式證據：基準版 `recordAnswer()` 與 `completeSession()` 沒有事件識別；同一 click handler 重入、頁面異常重送，或同日重玩固定字陣，都會再次增加卡片 `seen/right/wrong`、總答題、活動與回合數。
- 影響：固定題可農精通、正確率、連續學習與成就前置條件，數據失去可信度。
- 修正策略：加入有上限的 `eventIds` 冪等紀錄；一般回合使用 session token，每日字陣使用 `日期＋題目 key` 的穩定 token。同日重玩仍可計算當次分數與刷新最佳，但不重複寫入學習成長。現行 `liushu.save.v1` key 與 schemaVersion 2 保持不變，匯入舊檔時自動補空陣列。
- 可驗收條件：相同 event id 呼叫兩次，只增加 1 次卡片、答題、模式統計與活動；同一完成 id 只增加 1 回合；同日同題第二次作答不改寫第一次的學習證據。

## G2-07｜對戰結算分兩次寫入，且 `battle.best` 永遠沒有用途

- 程式證據：基準版 `finish()` 先 `recordBattleWin/Loss()`，再 `completeSession()`，兩次各自持久化；中途寫入失敗可留下勝負有記、回合未記的半套狀態。存檔雖已有 `battle.best`，實際從未更新或顯示。
- 影響：勝場、公平統計與回合完成可能不一致；重玩也缺少可比較的長期目標。
- 修正策略：以 `recordBattleResult()` 一次完成冪等檢查、勝負、最佳答對數、回合與印記評估，再單次持久化；大師名單與結算畫面顯示個人最佳及是否刷新。
- 可驗收條件：同一場結算呼叫兩次仍只有 1 勝、1 回合，最佳保留第一次有效的 7/10，不被重入的 10/10 覆蓋。

## G2-08｜今日任務可能把玩家送去尚未解鎖的大師，弱點任務也未鎖定弱點

- 程式證據：基準版 `todayMission()` 取第一位 `mastered < unlock` 的大師後直接回傳 `mode:'battle'`；按弱點任務 CTA 也只 `LSApp.go('flash')`，沒有呼叫 `LSFlash.focus()`。
- 影響：任務文案承諾的行動無法完成，削弱選擇感與對系統建議的信任。
- 修正策略：優先挑戰「已解鎖且未擊敗」的大師；下一位仍鎖定時，明示目前精通數／門檻並導向閃卡。弱點任務攜帶真實 `focusIds`，點擊後建立指定牌組。
- 可驗收條件：精通 0 字且只有解鎖門檻 8 的李斯時，任務為 `unlock` 並導向 flash；有門檻 0 且未擊敗的大師時才導向 battle；弱點 id 會原樣交給牌組。

## G2-09｜失敗後只能重來或繞去戰績頁，沒有短而明確的恢復路徑

- 程式證據：基準版自測結算只有再玩／對戰；對戰結算只有再戰／重選／看弱點，當回合答錯字沒有形成可執行的小任務。
- 影響：低分玩家在最需要降低挫折時，被迫重跑整局或自行尋找錯字，失敗成本過高。
- 修正策略：自測與對戰都收集本回合錯字，和既有弱點合併去重後最多取 5 字；結算直接提供「補強錯字」，鎖定閃卡牌組。概念錯題沒有假字卡，不會混入。
- 可驗收條件：`['a','b','a']` 加既有弱點 `['c','d','e','f']` 只產生 `['a','b','c','d','e']`；結算按鈕會先 `LSFlash.focus()` 再前往 flash。

## G2-10｜總正確率混合三種難度情境，玩家看不出問題在哪裡

- 程式證據：基準版只有 `quiz.answered/right/byCat`；一般自測、固定每日題與不同攻擊力／題限的大師全部混成一個總正確率。`battle` mode 雖存在於 recent，戰績畫面沒有模式拆分。
- 影響：玩家無法區分「一般辨識不穩」或「只在對戰壓力下失常」，回饋不足以支持下一個選擇。
- 修正策略：新增相容的 `quiz.byMode`，逐答累計 quiz／daily／battle；戰績新增三模式正確率。舊存檔沒有此欄位時顯示「—」，不反推或偽造歷史數字。
- 可驗收條件：三種模式分開累計；安全匯入只接受白名單模式與非負整數；舊檔可載入且不產生虛構分數。

## 發布驗收

1. 七個允許修改的 JavaScript 檔案全部通過 `node --check`。
2. `npm run logic` 覆蓋上述十項契約，且真實題庫仍維持題組無重複 `charId`。
3. `npm test` 的 validate、content、logic、smoke 全部通過。
4. `localStorage` key 仍為 `liushu.save.v1`、schemaVersion 仍為 2；舊 cards／quiz／battle／days 可遷移。
5. 同一答題事件與同一結算事件重送不增加任何學習量；每日字陣重玩只更新可比較的首次／最佳成績。
